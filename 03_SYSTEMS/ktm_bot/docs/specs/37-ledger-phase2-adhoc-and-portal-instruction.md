# 指示文37: 募集台帳DB化 フェーズ2（都度募集のDB化・Portal側の参加者取得のDB化）

作成: 2026-11-23（Muse）
対象: 03_SYSTEMS/ktm_bot、04_PORTAL
前提: フェーズ1（指示文35）で週末定期カスタムの DB 化が完了し、`recruitment_participants` テーブルと Worker 側ユーティリティ（`recruitmentLedger.js`）が存在する。本指示文はユーザー判断（2026-11-23）で残り2件を進めるもの。

## やること

### 1. 都度募集の DB 化
- `/recruit` とクイック募集の参加・変更・辞退も、定期募集と同じく `recruitment_participants` を正とし、カードは DB から再描画する形に移行する。既存のユーティリティを再利用し、方式を定期募集と揃えること。
- 都度募集には帯ロビーの概念はない（lobby は 'all' を使う。設計書34の定義どおり）。
- DB の行が無い既存の都度募集カードは、従来の本文パースにフォールバックして壊さないこと。
- 放置募集の自動クローズ（6時間）など、都度募集まわりの既存の振る舞いは維持する。

### 2. Portal 側の参加者取得を DB クエリに置き換える
- 04_PORTAL のオンボーディング管理（`periodicCustomCard.ts`）が Discord API 経由でチャンネルメッセージを走査・本文パースして参加者を取得している箇所を、`recruitments` / `recruitment_participants` への DB クエリに置き換える。
- 取得できる情報の内容（誰が・どの参加形態で参加しているか）が従来と同等以上になることを確認する。従来方式でしか得られない情報がある場合は、無理に置き換えず、その差分を報告すること。
- Portal の本番で、オンボーディング管理の表示が従来どおり出ることを確認する。

## やらないこと
- 定期募集（フェーズ1）の方式変更、判定基準・時刻の変更。
- 参加者一人ひとりの行の表示形式の変更。

## 完了条件
- Bot: `npm run dryrun:recruitment` に都度募集の DB 駆動ケースを追加し、全ケース PASS すること。
- Portal: `npm run build` 成功と、本番でのオンボーディング管理表示の確認結果を報告すること。
- 変更ファイルの一覧と、項目ごとに移行した処理・フォールバックの残り方を報告すること。
