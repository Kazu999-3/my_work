# 指示文34: 募集台帳のDB化に向けた調査と設計案の提出（実装はしない）

作成: 2026-11-23（Muse）
対象: 03_SYSTEMS/ktm_bot（必要に応じて 04_PORTAL の関連コードの読み取りは可）
経緯: ユーザーが 2026-11-23 に「募集台帳のDB化を改修したい」と決定。ただし現行の `recruitments` テーブルへの書き込みが best-effort で、実測0行だった時期がある（失敗の原因が未特定）。原因が分からないまま実装に入ると同じ失敗を繰り返すため、本指示文ではまず調査と設計案の提出までを行う。実装は設計案へのユーザー承認の後、別指示文で行う。

## 現状の理解（棚卸しより）
- 参加者名簿の実体は Discord の募集カード本文であり、Bot はカード本文をパースして集計している（`src/utils/recruitmentStatus.js` 等）。
- 重複防止もチャンネル内の既存メッセージ走査に依存している。
- `recruitments` テーブルへの書き込みは試みられているが best-effort 扱いで、過去に定期募集で実測0行だった旨がコード内コメントに残っている。

## 調査してほしいこと
1. `recruitments` への書き込みが成立しない／しなかった原因の特定。書き込み経路（定期募集・都度募集のそれぞれ）ごとに、どこで・なぜ失敗し得るかをコードと Supabase 側の制約（RLS、必須カラム、型など）から洗い出す。可能なら現在のテーブル実態（行数、定期募集分の有無）も確認する。
2. カード本文パースに依存している箇所の全量リスト（集計、重複防止、カード再構築、終了処理など、本文が「正」になっている処理の一覧）。
3. DB化した場合の影響範囲（Portal 側が `recruitments` や参加情報を参照している箇所があるか）。

## 設計案に含めてほしいこと
- 正を DB に置く形の提案：どのテーブルに何を持つか（既存 `recruitments` の拡張か、参加者テーブルの新設か）、カード本文は表示専用として DB から再生成する流れ。
- 移行の段取り：既存の本文パース方式と併用する期間の有無、切り替え手順、失敗時に本文方式へ戻せるか。
- 対象範囲の提案：定期募集だけ先にやるか、都度募集も含めるか（それぞれの規模感）。
- リスクと未決事項（ユーザーが判断すべき点）を明記すること。

## 成果物
- 調査結果と設計案を `03_SYSTEMS/ktm_bot/docs/reports/34-recruitment-ledger-db-design.md` に提出すること。

## やらないこと
