# 指示文35: 募集台帳のDB化 実装（フェーズ1：週末定期カスタム）

作成: 2026-11-23（Muse）
対象: 03_SYSTEMS/ktm_bot、04_PORTAL/supabase/migrations（マイグレーション置き場）
前提: 設計報告書 `03_SYSTEMS/ktm_bot/docs/reports/34-recruitment-ledger-db-design.md`。未決事項4点はユーザーが 2026-11-23 にすべて推奨案で承認した（下記「確定事項」）。

## 確定事項（ユーザー決定 2026-11-23）
1. **過去データの掃除**: 移行前に、`start_at` が7日より古い `open` のままの `recruitments` レコードを一括で `closed` に更新するクリーンアップを行う。
2. **切り替えタイミング**: 水曜12:00の定期募集カード新規投稿に合わせて適用する。既存カードからの引き継ぎ（シード）はしない。
3. **辞退者のデータ**: 論理削除（`is_cancelled` フラグで履歴を残す）。
4. **対象範囲**: フェーズ1は週末定期カスタムのみ。都度募集は現行方式のまま触らない。

## やること（設計書 §8 のステップに沿う）
1. **マイグレーション**: 設計書に基づき `recruitment_participants` テーブルを新設し、RLS ポリシーを配備する（Bot の service_role で読み書きできること、anon で書けないことを確認）。あわせて確定事項1のクリーンアップ SQL を実行する。
2. **Worker 側 DB ユーティリティ**: 参加・参加形態の変更・辞退の UPSERT と、名簿取得の関数を用意する。帯ロビーの決定（推定MMR 1450境界、未設定者は中初級帯）・参加形態（style）の決定は設計書の定義どおり。
3. **periodicRecruit.js の刷新**: 参加・変更・辞退の正を DB にし、カード Embed は DB の内容から再描画する。本文パースによる名簿復元は定期募集については廃止する。
4. **eventNotify.js の刷新**: リマインド、「あと1名」、20:00開催判定の集計を DB 直読みに切り替える。判定分岐とロビー別ルール（土曜2ロビー・日曜は単一）は現行仕様をそのまま維持する。
5. **失敗時の扱い**: DB 書き込みに失敗した場合は握りつぶさず、管理者アラートに通知し、カード表示と DB が黙って乖離しないようにする（過去の anon キー問題の教訓）。

## 適用タイミング
- 本番適用は水曜12:00のカード投稿に間に合う形で行い、最初の DB 駆動カードがその投稿になるようにする。デプロイが水曜12:00を過ぎる場合は、その週は従来方式のカードが出ている前提で、翌水曜から DB 駆動になる旨を報告すること。

## やらないこと
- 都度募集（/recruit・クイック募集）の DB 化（フェーズ2候補、今回は対象外）。
- Portal 側の変更（`periodicCustomCard.ts` の Discord 走査を DB クエリに置き換える話は、今回の範囲外として報告に分けて記載する）。
- 参加者一人ひとりの行の表示形式の変更、判定基準・時刻の変更。

## 完了条件
- `npm run dryrun:recruitment` に DB 駆動の集計ケースを含め、全ケース PASS すること。
- マイグレーションの適用結果（テーブル作成・RLS確認・クリーンアップ件数）と、変更ファイルの一覧を報告すること。
- 本番適用のタイミング（どの水曜12:00から DB 駆動になるか）を明記すること。
