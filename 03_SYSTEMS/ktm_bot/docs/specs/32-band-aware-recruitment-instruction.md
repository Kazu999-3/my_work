# 指示文32: 定期カスタム募集を帯（ロビー）単位の集計・判定にする

作成: 2026-11-23（Muse）
対象: 03_SYSTEMS/ktm_bot
経緯: ユーザー確認（2026-11-23）。定期カスタムの大前提は「上位帯と中初級帯は基本的に完全に分けて、それぞれ10人集める（独立した2ロビー）」。繰り上げ・格下サポートは不足時の穴埋めであり、Portal バランサー側の処理。現行 Bot はカード全体を合計10名で数えて一括判定しており、この前提に合っていない。本指示文で Bot の集計・判定をロビー単位に改める。イメージ図（Muse 側で作成したモック）でユーザー確認済みの形にする。

## 前提・用語
- 帯の境界は Portal と同じ推定 MMR 1450（1450以上＝上位帯、未満＝中初級帯）。参加者の帯は、参加時に引いている名簿データの推定 MMR で決める。
- カードは曜日ごとに1枚のまま変えない。カードの中に「上位帯ロビー」「中初級帯ロビー」の2つの枠を持ち、それぞれ定員10名で数える。

## やること

### 1. 募集カードの構造
- 参加者一覧をロビー別に分けて表示する（見出しは帯名「上位帯ロビー」「中初級帯ロビー」）。各ロビーに現在の人数と残り枠が分かる表示にする。
- 参加者一人ひとりの行の表示形式は現行のまま変えない（帯バッジ等の追加をしない）。
- 参加ボタン・参加形態（フル／1戦のみ／途中参加／観戦）の操作は現行のまま。参加した人は、その人の推定 MMR の帯のロビーに入る。

### 2. 集計とリマインド
- 人数の集計はロビーごとに行う（第1戦に出られる人数＝フル参加＋1戦のみ、の考え方は現行のままロビー単位に適用）。
- リマインド（金曜19:00・当日17:00）は、ロビーごとの状況（参加数/10、残り枠）を併記する。両ロビーとも満員なら送らない（現行ルール踏襲）。
- 「あと1名」の呼びかけはロビーごとに出し、不足している帯を名指しする（例：中初級帯あと1名で開催確定）。

### 3. 20:00 開催判定をロビーごとに行う
- 現行の判定分岐（開催確定／第2戦から開催／観戦者への参加お願い／助っ人募集／中止）を、ロビーごとに独立して適用する。片方のロビーだけ開催確定、もう片方は助っ人募集や中止、という結果があり得る。
- 助っ人募集は、不足している帯を指定して出す。
- 中止になったロビーがあっても、開催確定したロビーは通常どおり進める。カード自体の終了処理（月曜の後片付け含む）は現行のままカード単位。
- 指示文31の項目3（観戦者への参加お願いの自動化）を実施済みの場合は、その自動確定もロビー単位で動くようにする。

### 4. 数え方の境界
- Bot の集計は「本人の帯」で数える。繰り上げ希望・格下サポートの意向は Bot の集計には入れない（当日の穴埋めは Portal バランサーが行う）。ただし判定文や助っ人募集の文面で、Portal 側で穴埋めがあり得ることに触れるのは可。
- 推定 MMR が取得できない参加者（名簿に無い等）の扱いは、現行の参加処理の扱いに合わせ、どう扱ったか報告すること。

## やらないこと
- 募集カードを帯ごとに分ける（カードは曜日ごとに1枚のまま）。
- Portal（04_PORTAL）・バランサーのロジック変更。判定の人数基準そのものの変更（各ロビーに現行基準をそのまま適用する）。
- 指示文30・31と重なる変更のやり直し。実施順は 30 → 31 → 32 を想定し、先行分を前提に作業すること。

## 完了条件
- `npm run dryrun:recruitment` にロビー別のケース（片方だけ満員、片方だけ中止、両方満員 等）を追加し、全ケース PASS すること。
- 変更ファイルの一覧と、ロビー別の集計・判定がどう動くかの説明を報告すること。
