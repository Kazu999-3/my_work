### 🛡️ /admin ゲート（proxy.ts）のDiscord管理者セッション未対応解消（無限リダイレクトぐるぐるの完全根絶）

**概要**:
1. **背景と目的**:
   - ユーザーから「システム全貌仕様ガイドと戦術取り込みページがぐるぐるして開けない」との報告。

2. **原因と方針決定（Decisions Over Artifacts）**:
   - **真因の特定（プロキシとログイン画面の無限ループ）**:
     1. Next.js 16 のルーティングゲートである [`04_PORTAL/src/proxy.ts`](file:///d:/my_work/04_PORTAL/src/proxy.ts) が、パスワード用の `admin_session` クッキーしか検証しておらず、Discord OAuthセッション（`ktm_user_session`）を全くチェックしていなかった。
     2. そのため、Discord管理者（かずき）でログインしているユーザーが `/admin/*`（`/admin/guide` や `/admin/knowledge`）を開こうとすると、`proxy.ts` が「未認証」と判定して `/login` へ 307 一時リダイレクトしていた。
     3. `/login` 画面ではマウント時にスピナー（`border-t-amber-600 rounded-full animate-spin`）を表示しながら `/api/auth/verify` を呼ぶが、API側（`adminSession.ts`）はDiscordセッションを認識して「有効」と返すため、`router.replace("/admin/dashboard")` を実行。

### ⚠️ バランサーサイド偏り修正の第1回試み（`fix(balancer): サイドのBLUE/RED偏りを正しく均等化`）→ **後に不完全と判明**

**原因**: `buildBalanceResult` 内のサイド公平化ロジック（`balancer.ts` L719〜736）が、BLUEとREDの累計回数の単純な比較になっており、個人ごとの偏り差を相殺する計算になっていなかった。全員がBLUEに偏っているケースでは両スコアが拮抗してランダム選択になり、偏りが解消されなかった。

**このコミットでの修正内容**: 各プレイヤーの `BLUE - RED` 偏り差（bias）を算出し、`biasNormal`/`biasSwapped`という合計値同士を比較する方式に変更。

**⚠️ 追記（同日後刻の深層監査で発覚）**: この修正は `Math.abs()` を**合計後の最終比較にしか付けておらず、各項には付けていなかった**ため、A側+1・B側−1が5人ずつで必ず相殺し `biasNormal === biasSwapped` が常に成立する数学的恒等式バグを解消できていなかった（旧ロジックと同じ症状が形を変えて再発しただけだった）。真の修正は下記「潜在不具合5件の実装完了」を参照。

**3行ナレッジ**:
1. 累計回数の比較では「全員がBLUE偏り」のような同質ケースを正しく扱えない。`差分（bias = BLUE - RED）`を個人ごとに算出する発想自体は正しかった。
2. **教訓**: 符号付き合計を先に取ってから絶対値を付けても、+1/-1が人数分相殺されていれば意味がない。`Math.abs()`は「個々の項」に対して付けないと恒等式バグを解消できない。次回同種の「公平性判定」ロジックをレビューする際は、実際に具体的な数値（例: 全員BLUE偏り+3）を代入して手計算で確かめること。
3. `|biasNormal| === |biasSwapped|` の時のみランダム → それ以外は必ず決定論的に選択、という設計方針自体は正しかった（実装のバグだった）。

### ⚖️ 決定の経緯 ＆ 没理由 (Decisions Over Artifacts)
- **採用**: 検索APIのオンデマンド・インメモリTTLキャッシュ（5分間有効）。
  - *没案*: サーバー起動時に全件を読み込み、ファイル監視（chokidar等）で永続常駐させる案。
  - *没理由*: Next.jsのServerless環境（Vercel等）ではプロセスが永続常駐しないためファイル監視が機能しない。TTL方式（5分）であれば初回リクエストでメモリに載り、一定時間経過で再取得されるためサーバーレス環境とローカルの両方で安全にスケールする。
- **採用**: 外部LLMを使わない Markdown + ルールベースの「ゼロコスト対面ブリーフィング」。
  - *没案*: 試合開始時にGemini APIへプロンプトを投げて最新のブリーフィング文を生成する案。
  - *没理由*: 毎試合API課金が発生し、ロード時間（約30秒〜1分）の間にAPI通信遅延（2〜4秒）や429クォータ枯渇が起きた場合に画面に出ないリスクがある。すでに帝国に存在する確定知見（バイブル）をパースする方が、0円・0ミリ秒・100%の信頼性で即座に表示できる。
- **採用**: 敵の手持ちゴールドを「確定アイテム総額」＋「CS・キル等からの推定未消費ゴールド」として二重表記する設計。
  - *没案*: 敵の現在手持ちゴールド（currentGold）を直にAPIから取得しようとする案。
  - *没理由*: Riot Live Client Data API ではウォールハック（不正なリコールタイミング看破）防止のため、他プレイヤーのcurrentGoldは意図的に非公開とされている。存在しない値を捏造せず、確定値と推定値を明確に区別して表示することで規約と信頼性を両立。
