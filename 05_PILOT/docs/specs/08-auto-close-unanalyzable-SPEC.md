# SPEC 08: 解析不可動画の自動プレイリスト退避＆クローズ（05_PILOT／YouTube解析パイプライン）

## 目的
- 技術的に解析できない動画を、人の操作なしで「手動確認用プレイリスト」へ退避し、キューをクローズするまでを完全自動にする。キュー画面に滞留し続ける終端エラーをなくす。

## 現状（2026-11-20 コードと本番で確認済み）
- キュー（youtube_queue）のステータスは pending / completed / error_generation / error_no_transcript / failed / on_hold / manually_closed。
- 終端エラーの内訳：error_generation＝リトライ上限（MAX_RETRY）到達で打ち切り、failed＝削除・非公開・地域制限など解析不可、error_no_transcript＝字幕が無く Whisper 文字起こしも失敗。
- 手動版の仕組みは既にある：キュー画面（/admin/youtube）で動画を選ぶと「手動確認用プレイリストへ追加してクローズ」ができ、追加には既存の API（/api/youtube/playlist/add）と認証、プレイリスト ID（YOUTUBE_MANUAL_REVIEW_PLAYLIST_ID）が使われている。ただし人が選択・実行しないと進まない。
- 終端エラーの動画はキューに残り続け、ダッシュボードの「要対応」に上がり続ける（2026-11-20 朝時点でエラー4件）。
- 一時的な失敗は対象外にする区別が既にある：Gemini の利用上限（429）やレート制限で失敗した動画は retry_count を消費せず pending に戻る。この区別は壊さないこと。

## やること
- [ ] **自動退避処理の追加**：常駐ワーカー（scripts/youtube_worker.py）の処理サイクルに、終端エラーの自動退避を組み込む。対象ステータスは error_generation / error_no_transcript / failed の3種のみ。
- [ ] **既存の仕組みを再利用する**：プレイリスト追加は既存の API・認証・プレイリスト（手動確認用プレイリスト）を使う。新規の認証取得や別のプレイリスト作成はしない。既存の仕組みがワーカーから使えない場合は、無理に作り直さず、その旨と代替案を報告する。
- [ ] **追加成功したものだけクローズする**：プレイリスト追加が成功した動画だけを manually_closed に変更する。追加に失敗（API エラー等）した動画はステータスを変えず、次回サイクルで再試行する（取りこぼして消さない）。
- [ ] **ドライランモードを用意する**：対象一覧（件数・タイトル・ステータス内訳）を出力するだけで、追加もクローズもしないモード。導入時はまずドライランで実行し、結果を報告する。
- [ ] **ON/OFF スイッチ**：自動処理を環境変数で止められるようにする。既定は OFF で導入し、ドライラン結果の報告後、末吉の指示で ON にする。
- [ ] **結果を通知に残す**：自動クローズした件数と、追加に失敗して残った件数を、ワーカーの通常通知／ログに含める。失敗が続いていることが埋もれない形にする。
- [ ] 導入前にドライランの実行結果（対象一覧）を報告に含めること。Python 側の既存テストがある場合は通すこと。

## やらないこと
- 対象の拡大：pending / completed / on_hold / manually_closed には一切触らない。429・レート制限など一時的な失敗を終端エラー扱いにしない。
- プレイリストの新規作成・変更、YouTube 認証情報の新規取得。
- キュー画面（/admin/youtube）の手動機能や、承認画面など他の画面の変更。
- 解析処理そのもの（字幕取得・文字起こし・記事生成）の変更。

## 完了条件
- ドライランで対象一覧が正しく出力され、対象外（pending 等）が混ざらない。
- 自動運用 ON 後、終端エラーの動画がプレイリストに追加され manually_closed になり、監視で再検出されてもキューに戻らない。
- プレイリスト追加に失敗した動画はクローズされずに残り、失敗が通知で分かる。

## 未決事項（エージェントが勝手に決めない）
- 自動運用を ON にするタイミング（ドライラン報告を見て末吉が判断）。
- 過去に滞留している終端エラー全件を初回から対象にするか、運用開始後の新規分だけにするか（ドライランの件数を見て末吉が判断。既定は全件対象）。
