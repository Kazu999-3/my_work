# SPEC 03: 認証セキュリティ残件の仕上げ（パイロット）

## 目的
SPEC 02（コミット 6b0c3d2f）のレビューで見つかった残件を潰し、認証まわりを「完了」と言える状態にする。

## 現状（2026-11-19 レビューで確認）
- セッション方式・fail-closed・clientIp 対策は正しく実装された。一方で以下が残っている。
  1. `/api/auth/revoke` が実質無認証で、ボディで指定された任意の sessionId を失効できる（proxy の認証対象から `api/auth/` 全体が除外されているため）
  2. 失効の DB 永続化が失敗しても成功扱いになり、インメモリのみに残る（コールドスタートで失効が消える可能性）。失効チェック自体も DB エラー時に素通り（fail-open）
  3. 署名シークレット `PILOT_SESSION_SECRET` 未設定時は合言葉が HMAC 鍵を兼ねる
  4. 旧開発合言葉の文字列が `KNOWN_INSECURE_DEV_TOKEN` としてコード内に残っている（ログインには使えないが、SPEC 02 の完了条件「リポジトリ内に合言葉のハードコードが残っていない」は字義通り未達）
  5. レート制限のテストに、fail-closed（基盤が使えない場合）と上限到達の境界ケースがない（`isLoginBlocked` を呼ぶテストがない）
  6. `supabaseClient` の anon キーへのフォールバック時、ログイン失敗の記録（書き込み）が実際に機能するか未確認

## やること
- [ ] 失効APIの認証: `/api/auth/revoke` は、呼び出し元の Cookie にある自分自身のセッションだけを失効できるようにする。他人の sessionId をボディで指定しても失効できないこと
- [ ] 失効の永続化を正直にする: DB 書き込みが失敗した場合は成功として扱わず、エラーを返しログに残す。失効チェックは DB エラー時も、少なくとも同一インスタンスで失効済みの ID を素通りさせない
- [ ] 署名シークレット: 本番環境で `PILOT_SESSION_SECRET` が未設定の場合、起動時／ログイン時に明確な警告ログを出す（ログイン自体は止めない）。※シークレット自体の設定はユーザーが Vercel で行う。設定前にコード側を必須化してログインを壊さないこと
- [ ] 旧開発合言葉の文字列をリポジトリから消す: ブラックリスト照合は値のハッシュ（SHA-256）同士の比較に変え、文字列リテラルがコード・テストのどちらにも残らないようにする。テストも合わせて更新する
- [ ] レート制限テストの追加: (a) 基盤が使えない場合に `unavailable` となりログインが 503 になるケース、(b) 失敗回数が上限に達したらブロックされる境界ケース。`isLoginBlocked` を実際に呼ぶテストにすること
- [ ] anon フォールバック時の書き込み可否を検証し、結果を報告する: service role キーが無い構成で `recordLoginFailure` の書き込みが RLS で弾かれていないか。弾かれている場合は、ユーザーが Supabase 側で必要なポリシー変更を報告に明記する（設定変更自体はユーザーが行う）
- [ ] プロセス: 05_PILOT 以外のファイル（02_FACTORY/DAILY_LOG.md 等）を同じコミットに混ぜない。作業ログは別コミットに分ける

## やらないこと
- セッション方式そのものの作り替え（SPEC 02 の方式を前提に残件だけ直す）
- 本番の合言葉や環境変数の変更（ユーザーが行う）
- 数字・表記の統一（SPEC 01 の範囲）

## 完了条件
- 上記チェック項目がすべて実装され、追加したテストが通る
- リポジトリ内を検索して旧開発合言葉の文字列が（SPEC 文書内の言及を除き）残っていない
- anon フォールバックの検証結果がコミットメッセージまたは報告に明記されている

## 未決事項（エージェントが勝手に決めない）
