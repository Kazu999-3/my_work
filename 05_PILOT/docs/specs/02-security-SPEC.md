# SPEC：認証まわりのセキュリティ改善（戦術パイロット）

対象：https://ktm-pilot.vercel.app （リポジトリ内 `05_PILOT`）
Antigravityへの渡し方：このファイルをリポジトリに置き「このSPECを読んで実装して」と指示する。
優先度メモ：ログイン試行制限のフェイルクローズ化（やること2）は、2026-11-26 の Supabase プラン変更より前に片付けるのが望ましい。

## 1. 目的
合言葉ログインの仕組みにある3つの弱点（Cookieに合言葉そのものが入っている／試行制限がDB障害時に無効化される／開発用の予備の合言葉が公開コード内にある）を直し、漏洩・総当たり・設定ミスに強い状態にする。利用者のログイン体験（合言葉を入れるだけ）は変えない。

## 2. 現状の問題（2026-11-19 コードレビュー）
1. Cookieの中身が合言葉そのもの
   - `src/lib/tokenAuth.ts` の `setAuthCookie` は、入力されたトークン自体をCookie値として保存し、`verifyToken` はCookie値と期待値の直接比較のみ。有効期間（`PILOT_COOKIE_MAX_AGE`）は1年
   - Cookieが漏れた＝合言葉が漏れたことと同義。合言葉を変えない限り、特定の端末だけを失効させることができない
2. ログイン試行のレート制限が fail-open（使えないと無制限になる）
   - `src/lib/loginRateLimit.ts` の `isLoginBlocked` は supabase が null なら `false`（ブロックしない）を返す。失敗記録も同じDB依存
   - `src/lib/supabaseClient.ts` は service role キーが無いと anon キーへフォールバックする設計で、その場合 `edge_tasks` へ書けず制限が効かない可能性がある。その状態では `api/auth/login/route.ts` の0.8秒遅延しか防御がない
   - 環境変数の設定ミスひとつで総当たり対策が静かに無効化される
   - あわせて `clientIp` が `x-real-ip` / X-Forwarded-For の末尾を採用している点も、Vercel環境で詐称できないか要検証
3. 開発用フォールバックの合言葉が公開リポジトリ内にハードコードされている（値はこのSPECに書かない）
   - `src/lib/tokenAuth.ts` の `DEFAULT_DEV_TOKEN`。本番では「未設定なら全拒否」「公開値そのものが設定されていたら未設定扱い」というガードはある
   - ただし判定は `VERCEL_ENV` / `NODE_ENV` の OR 条件（`isProduction`）に依存しており、production 判定にならない公開デプロイ環境があればそのまま入れてしまう

## 3. やること
- [ ] セッション方式へ移行する：合言葉はログイン判定だけに使い、CookieにはランダムなセッションID（署名付き）を持たせる。サーバ側でセッションを失効できる形にする。有効期限は短め＋更新方式（スライディング）にする
  - 既存の良い実装は維持する：定数時間比較、httpOnly / Secure / SameSite=Lax、`safeNext`（オープンリダイレクト対策）、proxy による一元保護
- [ ] レート制限を fail-closed にする：制限の基盤（DB）が使えない場合は、ログイン自体を 503 で止める。あわせて `clientIp` の取得方法を Vercel 環境で詐称できない形に検証・修正する
- [ ] `DEFAULT_DEV_TOKEN` をコードから削除する：ローカル開発でも `.env.local` での合言葉設定を必須にする。本番ガード（未設定＝全拒否、公開値＝未設定扱い）は維持する
- [ ] 認証まわりの単体テストを追加する：公開値の拒否、本番未設定時の全拒否、レート制限の境界（上限到達でブロック、基盤が使えない場合は 503）、セッションの失効。CI で test が回るようにする
- [ ] 移行時の影響を報告する：既存ログイン端末がどうなるか（未決事項の決定に従う）、変更したファイル、テスト結果

## 4. やらないこと
- 数字・表記の統一（SPEC 01 の範囲）
- 合言葉そのものの変更・配布方法の変更（未決事項の決定があるまで）
- ログイン画面のデザイン変更
- 認証以外の機能（辞典・コーチ・解析など）の変更

## 5. 完了条件
- [ ] Cookieに合言葉が含まれていない（ブラウザで実物のCookieを確認して報告）
- [ ] サーバ側で特定セッションを失効できる
- [ ] レート制限の基盤を止めた状態でログインが 503 になることを確認できている
- [ ] リポジトリ内に合言葉のハードコードが残っていない（検索結果で報告）
- [ ] 認証まわりのテストが追加され、CIで通っている

## 6. 未決事項（エージェントが勝手に決めない）
- 移行時に既存のログイン（1年保持でログイン中の端末）を全て無効化して入れ直してもらうか、移行期間を設けるか
- 開発用合言葉の削除にあわせて、本番の合言葉自体を変える（ローテーションする）かどうか
- セッションの有効期限の長さ（利便性とのバランス。例：30日＋更新、など）
