# 報告2（B-11）：review 単件承認の誤操作リスク

作成日: 2026-11-22  
対象: `05_PILOT`（`05_PILOT/src/app/admin/review/page.tsx`）  
根拠指示文: `05_PILOT/docs/specs/22-missing-reports-instruction.md`（SPEC 19 / 指示文21 の未決事項 B-11）

---

## 1. 現状の実装概要

`05_PILOT/src/app/admin/review/page.tsx` における単件承認 `approveOne`（L223-L276）は、一括承認 `batch`（L291-L295）や単件却下 `rejectOne`（L279-L280）と異なり、`confirm()` 等の確認ステップを挟まずに即時実行されます。

- **クリック操作**: 一覧カード上の単件承認ボタン、またはプレビューモーダル内の承認操作から `approveOne(item)` を呼ぶと即時に承認処理が走ります。
- **キーボード操作**: `handleKeyDown`（L549-L640）により、一覧表示中でモーダルが開いていないとき、`a` / `A` キーを押すと `approveOne(currentItem)`（L617-L621）が即時実行されます。

---

## 2. 誤操作が起きうる具体的な場面

### (1) 既存の誤爆防止ガードが効く範囲
`handleKeyDown` 冒頭（L551-L566）には以下のガードがあります：
- `INPUT` / `TEXTAREA` / `SELECT` / `contentEditable` にフォーカスがあるときはキー操作をスキップする（フォーム入力中の `a` 入力は保護される）。
- プレビュー／分解／再解析／比較のいずれかのモーダルが開いている間は、`Escape` 以外のショートカットを受け付けない。

### (2) ガードが効かず誤操作が起きうる場面
- **フォーカス外の状態で `A` キーを押した場合**: カード選択や `J`/`K` 移動の直後、またはボタンクリック等でフォーカスが `<input>` 外（`<body>` や `<button>`）にある状態で、日本語IME確定や別操作のつもりで `A` を押すと、**確認なしで現在フォーカス中のカード（`focusedIndex`）が即承認**されます。
- **隣接キーの打ち間違い**: 一覧では `J`/`K`（移動）、`Space`（選択）、`Enter`/`P`（プレビュー）、`A`（承認）、`X`（却下）、`D`（分解）、`E`（詳細展開）が割り当てられています。確認ステップがある `X`（却下）と違い、`A` だけ無確認で発火するため、`S` や隣キーとの誤打鍵がそのまま本番統合につながります。
- **モーダル閉じた直後の連打・ダブルタップ**: プレビューを閉じた直後やカード上で別ボタン（詳細・プレビュー等）を押すつもりのクリックミスで単件承認ボタンを押した場合も、確認なしで即実行されます。
- **スクロール後の意図しない対象承認**: フォーカス中のカード（`focusedIndex`）がスクロールで視界から少し外れた状態で `A` を押しても、その時点の `currentItem` に対して即承認が走ります。

---

## 3. 誤って承認した場合の影響と取り消し・復旧の可否

- **DB・教本への影響**:
  - 単件記事の場合、`action: 'approve'` により `personal_knowledge` の `review_status` が `approved` に更新され、設定に応じて `champion_facts` やレーンガイドへマージ統合されます。
  - **複数チャンピオン記事**（`!isPreviewing && item.isMultiChampion && !item.is_atomic`、L249）の場合、**中身確認なしの自動分解＆教本直接統合（`action: 'decompose_auto'`）**がそのまま走ります。
- **楽観的消去と失敗時の復元は「承認の取り消し」として使えるか**:
  - **使えません**。L230 の `removeFromList([item.id])` は画面表示から即座に消すだけであり、サーバーへの `POST` が失敗したとき（`!result.ok`、L269-L272）だけ `load({ silent: true })` で一覧へ戻す仕組みです。
  - サーバー処理が成功した時点で既に本番DB・教本へ統合されており、**review 画面上に Undo（承認取り消し）ボタンはありません**。誤承認に気づいた場合、管理者が `/admin/dict-maintenance` 等の「改定履歴」から手動ロールバックや再編集を行う必要があります。

---

## 4. 確認を足した場合の運用への影響

- **1件あたりの追加操作**: 現在の「1アクション（`A` キー1回 または クリック1回）」に対し、`confirm()` や確認UIを挟むと **+1ステップ（`Enter` または確認クリック1回）** が毎回増えます。
- **現在の承認待ち件数（約191件）規模での負担感**:
  - 191件すべてを単件承認で処理する場合、**追加操作は +191回**（合計 382アクション）になります。
  - ただし、一括選択（`Space` や「チャンプ確定のみ全選択」ボタン）＋ 一括承認（`batch`、こちらは既に確認ダイアログあり）を併用している場合は、単件承認を使う件数分だけ確認が増える形になります。

---

## 5. 確認ダイアログ以外の代替案（判断材料）

確認を一律で足す以外に、日常運用のテンポと安全性のバランスを取る選択肢として以下が考えられます（**どの案を採るかは未決定・ユーザー判断待ち**）：

1. **キーボード `A` 経由のときだけ確認を出し、ボタンクリックは即時承認のままにする**
   - 効果: IME状態や指のすべりによる「見えない `A` キー誤爆」を防ぎつつ、明示的なクリック承認のテンポを維持できる。
2. **承認直後に数秒間の「元に戻す（Undo）」トーストを出し、確定送信を3〜5秒遅延させる**
   - 効果: 1件あたりの操作数を増やさず（+0ステップ）に、誤操作した瞬間にだけ1クリックで止められる（ただしネットワーク送信を数秒遅延させる実装が必要）。
3. **複数チャンピオン記事（`decompose_auto`）など影響が大きい単件承認だけ確認を出す**
   - 効果: 一撃で複数教本へ自動分解・統合される高リスクケースだけ確認を挟み、通常の単件承認の速度を保てる。
4. **`A` キーの即時承認を無効化（または `Shift+A` 等の2キー同時押しへ変更）する**
   - 効果: 単一キーの誤打鍵による意図しない承認を構造的に防げる。
