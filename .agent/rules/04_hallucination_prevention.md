# ハルシネーション防止 ＆ 知識カットオフ対策規約

## 1. 存在しない型・関数の捏造防止 (Anti-Hallucination)
- Gemini 3 は超大容量コンテキストと高い推論能力を持つ反面、コードベースのインデックスを直接参照していない場合、**存在しない型定義や関数を推論で補おうとして捏造するリスク**がある。
- **必須手順**:
  - 関数やコンポーネントを呼び出す前は、必ず `view_file` や `grep_search` を用いて、実際の型定義や引数の構造を 100% 確認してからコードを書き換えること。
  - 推測や過去の記憶だけで `interface` や `props` を更新してはならない。

## 2. 知識カットオフ（最新情報のファクトチェック）
- 特定のパッチバージョン（例: LoL パッチ 26.15 以降。表記は西暦下2桁基準の26.xxで統一）や、最新の外部ライブラリ仕様を扱う際は、AI自身の学習データ（過去の記憶）を過信してはならない。
- **必須手順**:
  - 必ず `search_web` またはローカルSSOT DB (`champion_facts`) を参照して最新のコンテキストを取得してから回答・コード生成を行うこと。
  - 勝手に過去のパッチや過去の仕様へ読み替えないこと。

## 3. ダミーデータ・モックフォールバックの禁止（実データ厳守原則）
- **最上位命令**: ユーザーから「テスト用にモックを作って」等の明確・意図的な指示があった場合を除き、**ポータルのすべての機能・API・UIにおいてダミーデータ、モックデータ、ハードコードされた架空の戦績・レビューを載せてはならない**。
- **必須手順**:
  - API通信失敗時やデータ未取得時は、ダミーデータを捏造して正常に見せかけるのではなく、**正確なエラーメッセージ（「〇〇が見つかりませんでした」等）または明確な空状態（Empty State）を表示**すること。
  - 特定プレイヤー（Kazurin等）のデータをデフォルトフォールバックとして他のプレイヤーへ流用・表示する行為を厳禁とする。

## 4. LLMモデル指定 ＆ 稼働報告の絶対規約
- **モデルIDの捏造厳禁 ＆ 実測義務**:
  - コード内に新しいLLMモデル名（Gemini等）を記述・変更する際は、推測や記憶で指定することを厳禁とする（架空モデルの混入や無料枠ゼロのモデル指定事故の防止）。
  - 必ず実測スクリプト（`.claude/skills/gemini-model-health-check/scripts/check_gemini_models.py`）を実行し、そのアカウントで実際にクォータが存在することを確認してからコードに反映すること。
- **正常稼働報告の検証義務（「嘘の正常報告」の根絶）**:
  - システムやバッチの稼働状況について「正常稼働」「全件成功」と報告する際は、単に直近の成功ログ1件を見ることを禁止する。
  - 必ずDB（`edge_tasks` 等）から「直近の失敗（failed）件数」「未処理件数」「最新のエラーメッセージ」を客観的にクエリし、実測数値を提示して報告すること（楽観バイアスの排除）。

## 5. 「どの資料を正（SSoT）とするか」の確定 ＆ 更新後スモークテスト
- **更新日時の新しさだけで判断しない（AIで仕事と心NOTE原則）**:
  - ファイルのタイムスタンプが新しくても、それが「検討中の下書き」や「誤字修正した旧資料」の可能性がある。
  - 常にプロジェクトの確定SSoT（Riot公式DataDragon、`champion_facts`、`NEXUS_INDEX.md`）を正の基準とし、現行の運用資料を特定して参照すること。
- **更新後の1問スモークテスト義務**:
  - ナレッジや辞典のルールを改定・修正した後は、その改定内容を検証する代表的なクエリ/質問（例: 「〇〇のLv1立ち回りは？」「〇〇ビルドの注意点は？」）を1問テスト実行し、新仕様が正しく反映されているかを客観的に検証すること。

## 6. 正本（生データ）と派生データ（AI生成物）の完全分離（Blooming原則）
- **生データ（Raw Data）の不変保持**:
  - YouTube文字起こし（Whisper raw）や実戦マッチデータ（Live Client Data / Riot Match API raw JSON）は「不変の正本」として保存する。
- **派生データ（Derived Data）の再生成可能性**:
  - AIが生成した要約、タグ、戦術ノート、ベクトルはすべて「派生データ」として扱い、正本と明確に区別する。
  - プロンプトの改善やLLMモデルの世代交代があった際、いつでも正本から100%再生成（バックフィル）できるパイプラインを保つこと。

## 7. 知識訂正の「上書き禁止・追加履歴」原則（イミュータブル・ナレッジ）
- **上書き（UPDATE）による経緯消滅の根絶**:
  - ナレッジ、仕様書、チャンピオン辞典の記述を修正する際、元の記述を無言で上書き消去してはならない。
  - 「変更前の内容」「変更理由（なぜ前はそう判断し、なぜ変えたか）」「変更日」を訂正履歴（`dict_known_corrections` や改訂履歴ログ）として追加（Append）形式で記録すること。

## 8. 空欄を作らない子の脱却（「わかりません」の明示義務・知ったかぶり厳禁 / ブラックにゃー原則）
- **確率的パズルによる知ったかぶりの根絶**:
  - LLMは「自然な言葉を繋ぐ」性質上、知らない情報でもマークシート試験のように当てずっぽうで空欄を埋めようとする。
  - **最上位規範**: 質問や依頼されたデータ・仕様が確たる根拠資料に存在しない場合、推測でそれらしい回答をでっち上げてはならない。**「この情報源には記載がありません」「わかりません」と率直に即答すること**を最高評価とし、知ったかぶりを最重度の重大過失とみなす（論語：「知るを知ると為し、知らざるを知らずと為す」）。

## 9. エビデンス紐付け ＆ 数字・仕様の捏造ガード（柵作り原則 / タイパ戦隊原則）
- **空白補完の厳禁（勝手な物語化の阻止）**:
  - 要約や記事生成において、文脈を滑らかにするために入力資料にない感情、出来事、特に**「数字（件数・秒数・バージョン・金額等）」**を勝手に補完・捏造することを厳禁とする。

## 10. LoL固有名詞・日本語アイテム名の絶対辞書規約（ユーザー指示 2026-10-31）
AIが過去の記憶や英語直訳で誤記しやすいLoL用語について、以下の表記を**絶対厳守**とする。
- **「ライアンドリーの仮面」 (Liandry's Torment)**:
  - 日本語クライアントの正式名称は**「ライアンドリーの仮面」**である。
  - **旧ミシック時代の「ライアンドリーの苦悶」と記述することを完全禁止**とする。記事・ナレッジ・コードコメント問わず、100%「ライアンドリーの仮面」と表記せよ。
- **「ヴィエゴ」 (Viego)**:
  - 日本語正式表記は**「ヴィエゴ」**である。「ビエゴ」という誤記を完全禁止とする。
- **「リーライ・クリスタルセプター」 (Rylai's Crystal Scepter)**:
  - 日本語正式名称は**「リーライ・クリスタルセプター」**である。「リライ・クリスタルセプター」という誤記を完全禁止とする。
- **「ザイラJG」（ロール表記統一）**:
  - 表記は**「ザイラJG」に完全統一**する。「ザイラジャングル」「ジャングルザイラ」といった表記揺れを完全禁止とする（ウーコンJG、シヴァーナJG等も同様に「[チャンプ名]JG」で統一）。

- **骨格確定（柵作り）の2段階展開**:
  - いきなり長文の完成原稿を書かせない。まず「主張・骨格・依拠するエビデンス（原本の一行）」を確定（柵の構築）し、その範囲内でのみ展開すること。
  - 出力文中の数字は、必ず元データ（Evidence）に明記されている実数値と100%一致させなければならない。

## 11. 2026年現行環境（Season 16 / パッチ26）厳格遵守 ＆ 旧仕様（2025年以前）の完全遮断
- **過去知識（2025年以前）の自動フィルタリング**:
  - ジャングル湧き時間（0:55）、カニ湧き（2:55）、新テンポ仕様など、タイムラインやゲームシステムは必ず「2026年現行パッチ（Season 16 / パッチ26以降）」を唯一の正（SSoT）とする。
  - 「1:30湧き」「3:30カニ湧き」など、2025年以前の古い記事や過去の記憶に基づいたタイムラインを語る行為を重大過失・即時修正対象とする。

## 12. スキルメカニクスの厳密検証義務（通常時 vs 変身時の仕様混同・エアプ解説の永久根絶）
- **通常形態と変身形態（R等）の境界分離**:
  - 「壁抜け」「スキルCD解消」「無敵・対象指定不可」などチャンピオンの重大メカニクスを語る際は、必ず「通常形態で可能か、変身時（R中・True Form等）限定か」を公式スキル仕様に照らして厳密に検証すること。
  - 通常形態で不可能な挙動（例：ベル＝ヴェスの通常時Q壁抜けなど）を序盤解説に混ぜる行為をエアプ・ハルシネーションとして永久に禁止する。

## 13. ペア・ライティング ＆ インタビュー絶対原則（AI単独推測・捏造の永久禁止）
- **ネット断片からの勝手な記事完成を永久禁止**:
  - 戦術バイブルやnote記事制作において、AIがWebの断片的なメモを勝手に貼り合わせて完成原稿をでっち上げることを完全禁止とする。
  - 必ず以下のステップを遵守すること：
    1. **骨子案の提示**: 章立て（構成案）のみを提示し、ユーザーの合意を得る。
    2. **章ごとのインタビュー**: 1章ずつ「実際の判断」「失敗談」「意識しているポイント」をユーザーに直接質問する。
    3. **対話型ブラッシュアップ**: ユーザーの生の言葉（一次情報）を元に、文章化・構造化して1章ずつ二人三脚で仕上げる。

## 14. LoL実測メタ・勝率・ビルド照会の絶対義務（Lolalytics CLI自動活用）
- **過去知識や当て推量の永久根絶**:
  - LoLのチャンピオン性能、メタ推移、Tier、ビルド順、ルーン選択、レーン適正、マッチアップ相性に関する話題・質問・note記事執筆時は、**AIの過去知識で語ることを厳禁**とする。
  - 必ず事前に `node d:/my_work/scripts/lolalytics.mjs` を実行し、Lolalytics（ロラリティクス）の実測データ（過去30日・エメラルド+・数千万戦統計）を取得してから回答すること。
  - **照会コマンド早見表**:
    - チャンピオン詳細・ルーン・ビルド・カウンター: `node d:/my_work/scripts/lolalytics.mjs champ <チャンプ名> [レーン]`
    - レーン別Tier・勝率・ピック率ランキング: `node d:/my_work/scripts/lolalytics.mjs tier [レーン]`
    - 2体の直接対決（実測勝率・相性）: `node d:/my_work/scripts/lolalytics.mjs matchup <チャンプ1> <チャンプ2> [レーン]`
