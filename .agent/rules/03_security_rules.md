# セキュリティ・ガードレイル

## ツール実行の許可ルール
ツール実行（コマンド実行、ファイル書き込み等）の許可を求める際は、必ず**日本語**で説明し、以下のリスクを推定パーセンテージ(%)で提示する。
- **秘密漏洩リスク**: パスワードや秘密鍵が外部に漏れる可能性
- **外部送信リスク**: 外部サーバーに意図しないデータが送られる可能性
- **コード実行リスク**: 悪意あるコードが勝手に動作する可能性
- **設定変更リスク**: PCや環境の設定が書き換わる可能性

## パッケージ導入の「三重審査」
AIが新しいパッケージのインストールを提案した場合、人間は以下の3点を確認してから許可（y）を出す。
1. **実在性と信頼性**: npm/Googleで検索し、スター数やダウンロード数が十分か確認する。
2. **更新頻度**: 最終更新が数年前のものは避け、メンテナンスされているか確認する。
3. **Typosquatting確認**: パッケージ名が有名なものと酷似していないかを確認する。

## 環境・設定の保護
- **ignore-scripts**: `.npmrc` にて `ignore-scripts=true` を常時設定し、インストール時の悪意あるコード実行を遮断する。
- **シークレット管理**: `.env` や機密ファイルは絶対に `git push` せず、トークン類は定期的なローテーションを検討する。

## APIレートリミット保護戦略 (Rate Limit Protection)
バックグラウンドタスクや定期実行スクリプトで外部API（Gemini等）を呼び出す際は、無料枠の枯渇や過負荷を防ぐため、以下のガードレールを必ず実装すること。
1. **Exponential Backoff**: `429 Too Many Requests` や `503 Service Unavailable` を検知した場合は、必ず指数的バックオフ（徐々に待機時間を延ばすリトライ）を実装する。
2. **フォールバック**: メインモデルのクォータが枯渇した場合は、別モデルへのフォールバック（例: `gemini-2.5-pro` -> `gemini-2.5-flash`）を試みる。
3. **競合回避 (Jitter)**: 複数スレッドが同時にリトライしてAPIを叩くのを防ぐため、待機時間にランダムなジッターを付与する。

## クラウド資源（AIクォータ・Supabase転送量・ログ量）防衛の鉄則 (Zero Waste & Egress Defense)
開発時・テスト時・運用時を問わず、以下の「3大資源防衛原則」を最上位義務として徹底すること（ユーザーの意図しない課金・サービス停止の完全根絶）。

1. **AI消費クォータの防衛 (LLM Quota Defense)**:
   - ループ処理内での同期的なLLM直列呼び出しを完全厳禁とする（APIタイムアウト・429クォータ瞬殺の原因）。
   - 事前にモデルの健全性を実測し、枯渇しているモデルへのリトライを繰り返さない。
   - 分割知見の保存など構造化済みデータのDB保存時は、無駄な二次LLM呼び出しを排除し、DB直接書き込みで完結させる。

2. **Supabaseデータ転送量の防衛 (Zero Egress Policy)**:
   - ビルド時（`next build`）や開発起動時（`npm run dev`）に、Supabaseから巨大データ（数十MB）を毎回ダウンロードすることを完全厳禁とする。既存のローカルJSONが存在する場合は100%キャッシュを利用し、Egress消費を0MBに抑える。
   - APIエンドポイントで巨大テーブル（`personal_knowledge`, `matchup_sentinel` 等）を無条件全件フェッチ（`limit(1000)` で長文本文 `content` を含む全列取得など）することを厳禁とする。
   - 一覧表示では必要なカラム（`id, title, tags, char_count` 等）のみに絞り込み、巨大な本文は詳細・プレビューを開いた時のみオンデマンド取得とする。
   - 短時間の連続リロードやフィルター操作による多重クエリを遮断するため、サーバーサイドメモリキャッシュ（SWR / TTL 30〜60秒）を常設する。

3. **Supabaseログ流量の抑制 (Log Ingestion Cap)**:
   - 不要な高頻度ポーリング（5秒〜10秒間隔の連続フェッチ）を排除する。
   - 変更がない状態での不要な全件クエリ発行を停止し、月間ログ生成量（1GB制限）の超過を防止する。
