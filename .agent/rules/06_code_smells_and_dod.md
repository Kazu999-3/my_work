# AIコーディング規約：コードの臭い排除 ＆ 完成の定義（DoD）

本規約は、東大Codex研究所（@UT_Codex）および自律セキュリティ監査（Cloudflare security-audit-skill）の知見に基づき、本プロジェクトにおけるAIエージェントのコーディング・リファクタリング品質を最高水準に保つための行動規範です。
（適用場面：全てのコード新規作成、機能改修、リファクタリング。非適用場面：単なるメモや調査タスク）

---

## 1. 仕様策定 ＆ 完成の定義（DoD: Definition of Done）原則

AIは実装に着手する前に、必ず以下の「受け入れ条件」と「エッジケース」を脳内（または実装計画）で明確に定義すること。

### ① 3つの必須検証パス ＆ 作らない機能の明文化
1. **正常系**: 期待されるユーザー体験と具体的な入出力例（I/O Example）。
2. **異常系**: 通信タイムアウト、権限エラー、不正な入力に対する分かりやすいエラーフィードバック。
3. **エッジケース（境界値・極端な条件）**: 以下の代表的エッジケースを**最低3点**事前に想定し、防御策をコードに組み込むこと。
   - **空欄 / 未選択 / Null**: データが存在しない場合の Empty State（空状態表示）。
   - **重複（Duplication）**: 同名ユーザー、重複レコード、同名ロールが存在しても誤爆しないこと。
   - **二重送信（Double Submit） / 冪等性（Idempotency）**: 連打や再実行されてもDB二重加算や状態破壊が起きないこと。
   - **端数処理・型不一致**: 数値計算の丸め、文字列と数値の暗黙変換の排除。
   - **タイムゾーン / 文字コード**: JST（UTC+9）統一、UTF-8文字化けの防止。
4. **🚫 作らない機能（Out of Scope）の事前明文化（@ohno_katsuya 原則）**:
   - 実装計画を立てる際、「今回作らない機能（意図的見送り・次回以降のスコープ）」を最低1点明記すること。
   - AIが自律的に過剰な機能（未指定の複雑な設定画面、過度な汎用化など）を肉付けしてコードを肥大化させる事故を未然に防止する。

### ② 完成の定義（DoD）
- 単に「コードを書いた」「コンポーネントを置いた」では完了とみなさない。
- 「正常系・異常系・エッジケースの全パスで破綻しないこと」「型チェック（`npx tsc --noEmit`）とテストが通ること」を機械的実値で検証して初めて完了とする。

## 2. コードの臭い（Bad Smells）禁止令 ＆ 自律リファクタリング

AIがコードを記述・編集する際は、以下の「コードの臭い」を絶対に放置せず、指定されたリファクタリング技法を自律的に適用すること。

| コードの臭い (Bad Smell) | 判定基準 | 適用するリファクタリング技法 |
| :--- | :--- | :--- |
| **長すぎる関数 (Long Method)** | 単一の関数・ハンドラが **50行以上** | **「関数の抽出 (Extract Function)」**<br>責務ごとに小さな純粋関数へ分割する。 |
| **深いネスト (Deep Nesting)** | `if` やループの入れ子が **3段以上** | **「ガード節の導入 (Replace Nested Conditional with Guard Clauses)」**<br>早期return / continue で平坦化する。 |
| **マジックナンバー (Magic Numbers)** | 生の数値や固定文字列がコード内に散在 | **「定数の抽出 (Extract Constant)」**<br>`UPPER_SNAKE_CASE` で名前を付けて自己文書化する。 |
| **データの群れ (Data Clumps)** | 関数の引数が **4つ以上** 並ぶ | **「引数オブジェクトの導入 (Introduce Parameter Object)」**<br>TypeScriptの `interface` / `type` を定義してオブジェクトで渡す。 |
| **フェーズの混濁 (Tangled Phases)** | 検証・計算・DB書き込み・通知が1つの処理に混在 | **「フェーズの分離 (Split Phase)」**<br>①入力検証 ➔ ②計算・ロジック ➔ ③永続化 ➔ ④副作用（通知）に段階分離する。 |
| **デッドコード (Dead Code)** | 使用されていない変数・関数・import | **「不要コードの即時削除 (Remove Dead Code)」**<br>コメントアウトで残さずGit履歴に任せて削除する。 |

## 3. 自律セキュリティ監査（Security Audit）原則

機能実装やAPI作成・変更時、全世界公開直前の三柱（RLS・規約・HTTPS）に加え、以下の裏取り監査を自律実行すること。

1. **認証の多重防壁**:
   - 管理者専用APIには `verifyAdminSession` を適用しているか。
   - Botや外部連携APIには `verifyBotSecret` または `CRON_SECRET`（Bearer認証）を適用し、fail-open（未設定時に素通りする穴）を完全排除しているか。
2. **SQL / RLS 防御**:
   - 外部入力値をそのままSQL文字列結合していないか（パラメータ化クエリ・RPCの徹底）。
   - SupabaseテーブルにRLSが適用され、匿名キー（anon）からの直接改ざんが防止されているか。
3. **リソース保護（Vercel CPU / Egress）**:
   - 常時ポーリングや無駄なcronジョブで無料枠（Fluid Active CPU: 4時間/月）を圧迫していないか。

## 4. スロットマシン思考 ＆ クリーンロールバック基準（@Maruo_0314 / Anthropic社内原則）

AIによる自律実装において、失敗したコードにパッチを重ねて泥沼化する「コンテキスト汚染」を防ぐための行動規範。

1. **チェックポイント（Checkpoint）の徹底**:
   - リファクタリングや大きな機能追加に着手する前、必ず動作確認済みのクリーンな状態（Gitコミット）を確定しておくこと。
2. **スロットマシン思考（Slot Machine Mindset）**:
   - 実装をAIに任せ、もし方針が破綻したり予期せぬ多発エラーが発生した場合は、**小手先のパッチを延々と重ねない**こと。
   - レバーを引いて揃わなかったスロットのように、直前のチェックポイント（`git checkout` / `git restore`）へ一括ロールバックし、プロンプトや設計（計画）を見直して最初から綺麗な状態でやり直す。
3. **自己修復（Self-Healing）の3回打ち切りルール**:
   - 自動修復・修正試行は最大3回までとし、3回で解決しない場合は即座に作業を中断し、「Request Review（人間の確認待ち）」状態にして報告すること（グローバルルール第8項と完全同期）。
4. **反省の1行蓄積（Continuous Reflection）**:
   - セッション終了時、エラーや手戻りの原因となった反省点を、次回の行動を縛る「再利用可能な1行ルール」として `DAILY_LOG.md` または規約へフィードバックすること。

## 5. 仕様・ロジックの動的シミュレータ化原則（@kenta_feels_ayu 原則）

複雑な計算式、分岐ロジック、格差診断、オッズ計算、精算ルールなどを実装・改修する際、長文のMarkdownテキストや数式だけで説明することを避ける。

1. **動くモック（Interactive Simulator）の活用**:
   - 人間（ユーザー）が判断・味見するための資料として、スライダーやボタン操作で入力値を動かし、出力結果や警告バナーがリアルタイムに変化する「動的HTMLシミュレータ」を活用すること。
2. **エッジケースの直感的検証**:
   - 「0分投了」「極端なMMR差」「投票数0件」「上限キャップ超過」などの境界値を、画面上でポチポチ操作して視覚的に検証できる状態を作ることで、仕様漏れや認識齟齬をゼロにする。

## 6. ソロプレナーの継続哲学：新規に逃げず既存を1年磨く（@ohno_katsuya ＆ ぶべ氏 原則）

AIによってコードも文章も誰でも一瞬で作れる時代だからこそ、勝敗を分けるのは「ツールの使い方」ではなく「継続の姿勢」である。

1. **思いつきによる新規逃避の禁止**:
   - AIで簡単にプロトタイプができると、人間もAIも「次々に新しいアプリや新機能」の思いつきへ逃げがちになる。
   - しかし、市場の99%がこの「作っては放置」のサイクルで自滅していく。
2. **既存プロダクトを1年磨き続ける者が勝つ**:
   - 我々の核となる資産（KTMバランサー、05_PILOTのAIコーチ、コミュニティ、224本の戦術note）を信じ、不具合の撲滅、UIの改善、リファクタリング、セキュリティ強化を**1年間愚直に継続した者だけが競合ゼロの独走状態**を築くことができる。
   - 新規作成の誘惑に負けず、「今日あるものを昨日より1%良くする」改善を最優先せよ。
