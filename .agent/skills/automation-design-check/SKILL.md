# 自動化の設計チェック（4行シート・レベル・止まる5原因）

出典：プルぽち「Muse自動化の教科書2026年11月版」（2026-11-20 に読んだ記録の範囲で構成）。新しい自動化は、いきなり作らずこの手順で設計してから作る。

## 手順1：4行設計シートで書く

自動化の依頼・設計は必ずこの4行で書く。1行でも欠けたら設計が曖昧なまま進んでいるサイン。

- ****：何が起きたら／いつ動くか（時刻、イベント、新着の到着など）
- ****：何をするか（調べる、まとめる、下書きを作る、など）
- ****：結果をどこへ届けるか（チャット、ファイル、成果物置き場など）
- ****：どこで人の確認を挟むか／何は絶対に自動でやらないか（送信・応募・購入・削除などの線引き）

## 手順2：自動化レベルを決める（1〜5）

| レベル | 内容 |
| --- | --- |
| レベル1 | 知らせるだけ（検知して通知する） |
| レベル2 | まとめて届ける（収集・要約して届ける） |
| レベル3 | 下書きまで作る（送信・実行は人が行う） |
| レベル4 | スペース（成果物置き場）に貯める（成果物を蓄積し、人が取りに行く） |
| レベル5 | 承認つきで実行する（人の承認を経て実行まで行う） |

- レベルは**1段ずつ上げる**。新しい自動化は低いレベルから始め、安定してから上げる
- レベルを上げることは、ブレーキの位置を後ろへずらすこと。上げる前に4行シートのを書き直す

## 手順3：止まる5原因を先回りで点検する

自動化が止まる原因はほぼこの5つ。設計時に1つずつ潰す。

1. **承認待ち**：途中で人の承認が必要だと、承認されるまで止まる
2. **ログイン・決済の壁**：ログインや支払いが必要な手順は自動で越えられない
3. **サイト側の拒否**：アクセス先に自動アクセスを拒否される
4. **時間超過**：処理が長く、制限時間を超えて打ち切られる
5. **利用量上限**：API やサービスの利用量の上限に達する

- **止まってほしくない自動化は、承認不要の作業だけで組む**（原因1の回避）。承認が要る作業は、レベル3（下書きまで）で止める設計にする
- ログイン・決済が要る手順は自動化の外に出し、人がやる手順として明記する
- 時間超過と利用量上限は、対象を絞る・頻度を落とす・上限に達したら通知する、のいずれかで先に決めておく

## 手順4：週1回の点検ルーティン

- 週に1回、動いている自動化の一覧を点検する
- 見ること：止まっているものはないか／止まった原因は5原因のどれか／レベルを上げる・下げるべきものはないか／もう要らないものはないか
- 点検で見つけた変更は、4行シートを更新してから反映する

## 既存の自動化の位置づけ（例）

- 朝刊（毎朝のまとめ配信）、求人チェック（新着を集めてシートと報告へ）、締切ウォッチ（大事なメールを検知して知らせる）は、いずれも**ブレーキ付きのレベル1〜2**の設計：検知と要約までを自動化し、応募・返信・連絡などの実行は必ず人の判断を挟む
- 新しい自動化を頼まれたら、まずこの水準（レベル1〜2＋明確なブレーキ）で4行シートを書き、必要なら段階的に上げる提案をする
