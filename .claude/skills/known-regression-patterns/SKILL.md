# Known Regression Patterns（既知の再発パターン）

## 背景

このプロジェクトでは、同じ根本原因のバグが形を変えて複数回発生している。個別に直しても、次に似た処理を新規実装する際に同じ罠を踏みやすい。このスキルは「実装前のセルフレビュー用チェックリスト」として使う——スキル自体が何かを実行するわけではない。

## チェックリスト

### 1. Supabaseページネーション取りこぼし
PostgRESTの`.select()`は**デフォルトで最大1000件**しか返さない。件数が1000を超えうるテーブルへの集計・全件取得で素の`.select()`を使うと、件数が閾値を超えた瞬間に静かに一部データが欠落する（エラーにならないため気づきにくい）。
- **該当した実例**: `dictFactCheck.ts`の5箇所の集計クエリが1000件超で取りこぼしていた。
- **対処**: `04_PORTAL/src/lib/fetchAll.ts`の`fetchAllRows()`ヘルパーで`.range()`ページングすること。新規に「全件カウント」「全件突合」系のクエリを書く時は、そのテーブルが将来1000件を超える可能性があるかを必ず自問する。

### 2. チャンピオン名の正規化漏れ
Riot APIのチャンピオンID表記揺れ（大文字小文字、アポストロフィ、"MonkeyKing"⇔"Wukong"等）を正規化せずキー・マッチングに使うと、同一チャンピオンが別レコードとして重複する。
- **該当した実例**: ソロQ振り返りの`matchupId`生成、辞典の更新キュー。
- **対処**: チャンピオン名を主キー・外部キー・突合キーとして使う新しいコードパスは、必ず`04_PORTAL/src/lib/championNames.ts`の`normalizeChampionName()`/`resolveToRosterChampion()`を通すこと。

### 3. TOCTOU（チェック後書き込み）レース条件
「件数を確認してから閾値以下なら書き込む」という読み取り→書き込みの2ステップ処理は、並行実行（複数リクエスト・複数ワーカー）で容易にレースする。読み取り時点ではセーフでも、書き込み時点では既に閾値を超えている場合がある。
- **該当した実例**: `dict_fact_check_queue`の上限チェック（`PENDING_QUEUE_CAP`）、`soloq_reflections`の`match_id`重複（部分ユニークインデックス`ON CONFLICT`不一致問題、migration 53→54）。
- **対処**: 可能な限りDB側のユニーク制約・CHECK制約で保証する（アプリ側のcheck-then-actに頼らない）。キャップ系は「書き込み直前に再度ライブカウントを取る」等、チェックと書き込みの間隔を最小化する。

### 4. 孤立した自動化（Orphaned Automation）
生成・処理ロジック自体は実装されているのに、それを起動するスケジューラ/cron/GitHub Actions側の配線が漏れている、または存在しないケース。コードレビューだけでは「動くはず」に見えてしまう。
- **該当した実例**: このセッション以前に3件確認済み（詳細は[[project_orphaned_automation_pattern]]メモリ参照）。
- **対処**: 新しい定期実行・自動化処理を追加したら、それを呼び出す側（GitHub Actionsのworkflow、`edge_worker_daemon.py`のポーリング対象、cron設定）が実際に存在し、対象タスクタイプを拾えているかまで追って確認する。「関数を書いた」で終わらせない。

### 5. AIによるニッチな数値情報のハルシネーション
検索グラウンディングなしでAIに「〇〇の具体的な数値・タイミング」のような、学習データに頻出しないニッチな事実を生成させると、もっともらしいが誤った値を自信満々に返すことがある。
- **該当した実例**: ジャングル序盤タイミング自動取得で、AIが実際のパッチ変更を反映しない一般論的な数値を生成していた。
- **対処**: ニッチな数値系の自動生成は、(a) 検索根拠(citation)を必須にする、(b) 根拠が取れない場合はnull/取得失敗として明示し、それらしい値で埋めない、のいずれかを徹底する。プロンプトに「不明な場合は生成せずnullを返せ」と明記する。
- **一般原則（2026-08-10、外部記事の実装例より裏付け）**: これはLoLジャングルタイミングに限らない。「誤った断定」より「不明・判定保留」の方が実害が小さい場面(自動マッチング、自動判定、自動分類等)では、確信度が低い時に無理に確定させず「保留」「次回再判定」を選べる設計にする。判定を急がず、不確実なデータのまま確定させない方針を優先する。

## 使い方

このチェックリストはコード生成/レビュー時に頭の中で（または実際にコメントで）1〜5と照合するだけでよい。自動チェックスクリプトが必要なほど頻出する場合は、都度[[gemini-model-health-check]]のような専用スキルに切り出すこと。
