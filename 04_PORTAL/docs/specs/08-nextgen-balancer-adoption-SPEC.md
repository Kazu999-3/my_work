# SPEC 08: 次世代バランサー（nextGenBalancer）の正式採用に向けた監査・テスト・比較検証

作成: 2026-11-20（Muse）
対象: 04_PORTAL/src/lib/balancer/nextGenBalancer.ts / 04_PORTAL/src/lib/balancer.ts

## 背景

- `nextGenBalancer.ts`（263行、モンテカルロ1,000回シミュレーションによる予想試合時間・ワンサイド事故率、ボス相殺、スノーボール連鎖耐性、プレイスタイル衝突、当日疲労の平準化を謳う評価エンジン）が、指示外の変更として死リンク修正と同じコミット（8ba0468）で追加された。現状どこからも呼ばれていない未使用コード。
- 2026-11-19 の DAILY_LOG には「本番配備 ＆ 実戦実証」「単体テスト 25 passed」等の記述があるが、その時点で当該ファイルもテストファイルもリポジトリに存在せず、裏付けがない。
- ユーザー判断（2026-11-20）: 削除ではなく、正式採用の可否を判断できる状態まで持っていく。そのための監査・テスト・比較検証を行うのが本SPEC。既存バランサーは balancer.ts の `coreBalanceTeams` / `coreBalanceProposals`。

## Phase 1: 監査

- [ ] 評価ロジックを精査し、各評価（シミュレーション、ボス相殺、連鎖耐性、スタイル衝突、疲労平準化）が何を根拠に計算しているかを一覧化する
- [ ] 入力データの実在確認: `AssignedPlayer` のどの項目を使っているか。実在しないデータ（例: 取得できていないスタッツ）を仮定している箇所があれば明記する
- [ ] DAILY_LOG の先行記述（配備・実証・テスト合格）と実態の差分を、報告に明記する（日誌の記述自体は勝手に書き換えない）

## Phase 2: テスト

- [ ] `nextGenBalancer.test.ts` を新規作成し、評価関数の単体テストを実際に書く（日誌が主張した件数に合わせる必要はない。境界値・異常系を含める）
- [ ] 既存の balancer.test.ts と併せて全テストが緑になること

## Phase 3: 比較検証（シャドー評価）

- [ ] 過去の実際の対戦データ、または代表的な10名編成（複数パターン）で、既存バランサーの提案チームに対し nextGen 評価を並べて出す比較レポートを作る
- [ ] 予想試合時間・ワンサイド率などの出力が、実際の結果や体感と大きく乖離していないか所見を付ける

## やらないこと

- 本番のチーム分けロジックへの組み込み（呼び出し側の変更、UI 変更を含む）。統合方式が未決のため、Phase 3 までで止める
- 既存バランサー（balancer.ts）の挙動変更
- 他プロジェクトのファイルの変更

## 未決事項（勝手に決めない）

- 統合方式: 既存バランサーの置き換え / スコアへの併用 / 評価表示のみ、のどれにするか
- 疲労・ティルト平準化に使うデータ（当日の連敗数など）の取得可否と是非
- レーン別MMRサマリーの常時表示（既存の未決事項）と本エンジンの表示が関係する場合は、併せて判断材料を出す

## 完了条件

- Phase 1〜3 の成果物（監査一覧、テスト全緑、比較レポート）が揃い、ユーザーが統合方式を判断できる状態になっていること
- Portal の `npm run build` が成功してからプッシュすること
