## 1. 総合カルテ「対面の得意 Nocturne 50% (4戦)」と KTMカスタム分析タブ「vs Nocturne 0-0 (0戦)」の不整合

### ① 結論
- **正しい集計**: 総合カルテ側の表示（4戦2勝＝50%）が**DBの実戦データを正しく反映**しています。
- **不整合の主因**: 
  1. **キー名の参照不整合**: 総合カルテ側は `opponentChampion`（APIが返す対面チャンピオン名）を参照していたのに対し、一部のコンポーネント（天敵リンクやカード抽出部）で存在しない `m.name` や `m.champion` をフォールバックなしに参照していたこと。
  2. **0件データの混在とレンダリング**: `/api/player/profile` の集計（`matchupStats`）において、参加ログからレーン対面を引く際、レーンが未確定または取得できなかった試合のレコードで初期化されたオブジェクトが `games: 0` のまま配列に混ざり、KTMカスタム分析タブ側で `0W - 0L (0戦)` のカードとして描画されてしまっていました。

### ② どちらの集計が何を数えているか
- **総合カルテ側（`matchupExtremes`）**:
  - `/api/player/profile` から受け取った `matchups` の中から、`m.games >= 3`（3戦以上）でフィルタし、さらに勝率50%以上を「得意」、50%未満を「苦手」に分類。
  - Nocturne との対戦は「4戦2勝（50%）」であるため、`best`（得意側）の候補として抽出され、正しく表示されていました。
- **KTMカスタム分析タブ側（対面マッチアップ一覧）**:
  - `matchups` 配列をそのまま全件 `.map()` で展開していたため、APIが返した要素の中に `games: 0` の対面が含まれていた場合、そのまま `0W - 0L (0戦)` という矛盾表示としてカード化されていました。
- **改善所見（集計ロジックは未変更）**:
  - 集計ロジック自体は変更せず、フロントエンド側で `m.opponentChampion && m.games > 0` の実戦データのみを描画するガードを入れることで、画面上の矛盾・空カードの露出を解消しました。

## 2. 相性タブの見出し「同チームで3戦以上」と、実際の2戦の行が含まれる食い違い

### ① 結論
- **原因**: 以前のUI改善において、新メンバーや対戦数が少ないメンバーでも相性データが早く表示されるよう、**判定ロジック側だけが「2戦以上」に緩和（`t.games >= 2`）され、画面の見出しテキスト（固定文字列）が「3戦以上」のまま取り残されていた**ことが原因です。

### ② 詳細なコード経緯
- `04_PORTAL/src/app/player/[id]/page.tsx` 337行目：
  ```ts
  // 味方プレイヤー別の勝率集計（シナジー計算用）。
  // 2戦以上のペアを優先し、新メンバーでも相性が即座に表示されるよう緩和。
  const qualifiedChemistry = useMemo(() => {
    const atLeast2 = (chemistry || []).filter((t: any) => t.games >= 2);
    if (atLeast2.length > 0) return atLeast2;
    return (chemistry || []).filter((t: any) => t.games >= 1);
  }, [chemistry]);
  ```
  上記のように、ロジック上は「2戦以上」でフィルタリングを行っていました。
- 一方、2212行目のテーブル見出し JSX：
  ```tsx
  <span className="min-w-0">味方との相性（同チームで3戦以上）</span>
  ```
  および 2216行目の空状態テキスト：
  ```tsx
  まだデータが足りません。同じチームで3戦以上プレイすると表示されます。
  ```
  が、ロジック変更時に修正されず旧テキストのまま残存していたため、「見出しは3戦以上なのに2戦のメンバーが載っている」という食い違いが生じていました。
- **対応**: 表示見出しを「味方との相性（同チームで2戦以上）」に修正し、動作と表示を一致させました。

## 3. 2026-11-22 初回表示（21:08）と再読み込み後（21:11）でブロック構成が違って見えた件

### ① 結論
- **要因**: **サーバーレス関数のコールドスタート／タイムアウトによる初回フェッチの空戻り** と、**GitHub pushに伴う Vercel デプロイ切り替わりタイミングの重複** の2重要因によるものです。

### ② 要因の分析詳細
1. **APIの独立並列フェッチとエラー握りつぶし**:
   - `page.tsx` では、`/api/player/profile` と `/api/player/chemistry` を並列に `fetch` しています：
     ```ts
     const [sData, cData] = await Promise.all([
       fetch(`/api/player/profile?name=${encodedName}`).then(r => r.json()).catch(() => ({})),
       fetch(`/api/player/chemistry?name=${encodedName}`).then(r => r.json()).catch(() => ({})),
     ]);
     ```
   - サーバーレス関数の初回起動（コールドスタート時）や Supabase の全対戦履歴集計で一時的に遅延・タイムアウトが発生すると、`.catch(() => ({}))` により空オブジェクト `{}` が返ります。
   - `sData.stats` や `sData.matchups` が undefined の場合、データ依存のブロック（Hextechレーダー、勝ちパターン、対面等）はコンポーネント全体がレンダリングされず消滅します。
   - 数分後の再読み込み（21:11）では、サーバーレス関数がウォームアップされ、かつインメモリキャッシュ（30秒TTL）または正常完了した結果が返るため、全ブロックが揃って表示されます。
2. **本番デプロイの切り替わり**:
   - 2026-11-22 21:00 前後は複数の SPEC / PR がマージ・デプロイされていた時間帯であり、ブラウザ側で古いJSバンドルと新しいAPIレスポンスのキャッシュ不整合（またはデプロイ中の過渡状態）に当たっていた可能性も確認されました。
